# KCM SDK Community Guidelines

This document covers community guidelines specific to KCM SDK contributions. For general project guidelines, see the root [CODE_OF_CONDUCT.md](../CODE_OF_CONDUCT.md).

## SDK Community Standards

### Communication

- Be respectful and constructive in SDK-specific discussions
- Use language-appropriate terminology when discussing SDKs
- Focus on technical merit, not personal preferences
- Welcome newcomers to each language community

### Inclusivity

- Write examples and documentation that are accessible to all skill levels
- Avoid language-specific jargon without explanation
- Provide multiple examples when possible (basic, intermediate, advanced)
- Ensure documentation is available in clear, simple English

## SDK-Specific Conduct

### Cross-SDK Respect

- Do not disparage other programming languages
- Focus on trade-offs, not superiority
- Acknowledge that different languages have different strengths
- Support users regardless of their language choice

### Code Quality

- All SDK contributions must meet the same quality bar
- Do not submit "quick and dirty" implementations
- Every SDK deserves proper testing, documentation, and examples
- Language idioms should be followed, not fighting the language

### Support

- Respond to SDK issues within 48 hours
- Provide reproducible examples when debugging
- Guide users toward solutions, not just answers
- Document common pitfalls and solutions

## Reporting Issues

### Bug Reports

- Include SDK language and version
- Include minimal reproduction steps
- Include expected vs actual behavior
- Include environment details

### Feature Requests

- Explain the use case across languages
- Show proposed API for each affected SDK
- Consider cross-SDK consistency
- Reference SSOT requirements when applicable

### Security Issues

- Do not report security vulnerabilities through public issues
- Email security@kcm.dev for all security concerns
- See [SECURITY.md](../SECURITY.md) for details
