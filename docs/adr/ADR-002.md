# ADR-002: Volcano-Style Query Execution

## Status
Accepted

## Context
KCM needs a query execution model that supports:
- Lazy evaluation (don't compute until needed)
- Composable operators (chain filters, joins, aggregations)
- Memory efficiency (process one row at a time)
- Extensibility (add new operators without changing executor)

## Decision
Use Volcano-style pull-based execution where each operator implements a `next()` method that returns one row at a time.

## Consequences

### Positive
- Simple operator interface (Scan, Filter, Project, Join, Aggregate)
- Lazy evaluation avoids unnecessary computation
- Memory efficient (streaming execution)
- Easy to add new operators

### Negative
- Function call overhead per row (mitigated by batch processing)
- No automatic parallelism (added via rayon thread pool)

## Alternatives Considered

| Alternative | Pros | Cons | Decision |
|------------|------|------|----------|
| Materialized (full pipeline) | Fast for small data | Memory intensive | Rejected |
| Vectorized (batch) | SIMD-friendly | Complex implementation | Future optimization |
| **Volcano (chosen)** | Simple, memory-efficient | Function call overhead | **Accepted** |
