# ADR-010: 13-Crate Workspace Architecture

## Status
Accepted

## Context
KCM is a complex system with many components. Options for code organization:
- Monolith: Single crate, simple but hard to maintain
- Many crates: One per component, complex dependencies
- Layered crates: Group by responsibility, balanced

## Decision
Use 13 single-responsibility crates with clear dependency flow.

## Consequences

### Positive
- Clear responsibility boundaries
- Independent compilation (faster builds)
- Testable in isolation
- Reusable components

### Negative
- More complex workspace management
- Dependency version coordination (solved with workspace.dependencies)

## Crate Map

```
kcm-core          -> Types, DenseVec, Bitmap, Dictionary
kcm-storage       -> Columns, Codecs, WAL, FileFormat, Index
kcm-compute       -> Query operators, SIMD
kcm-reasoning     -> Rules, Inference
kcm-optimizer     -> Cost model, Planner, Statistics
kcm-runtime       -> Database, Transactions, Metrics
kcm-interface     -> C FFI, Python, REST, KQL
kcm-distributed   -> Sharding, 2PC
kcm-ml            -> Learned Index, Confidence Learner
kcm-security      -> RBAC, Encryption, Audit
kcm-compliance    -> GDPR, Classification
kcm-testing       -> Load, Stress, Security tests
kcm-server        -> HTTP, gRPC binaries
```

## Alternatives Considered

| Alternative | Pros | Cons | Decision |
|------------|------|------|----------|
| Monolith | Simple | Hard to maintain | Rejected |
| 5-6 crates | Fewer deps | Blurry boundaries | Rejected |
| **13 crates (chosen)** | Clear boundaries | More complex | **Accepted** |
