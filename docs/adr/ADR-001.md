# ADR-001: Columnar Storage Architecture

**Document ID:** ADR-001
**Version:** 1.0.0
**Status:** Accepted
**Author:** KCM Engineering Team
**Date:** 2026-08-04
**Deciders:** Architecture Guardian (P5)

## Context
KCM needs to store knowledge facts (subject-predicate-object triples with confidence) efficiently. Traditional row-based storage (like RDBMS) or pointer-based graphs have limitations:
- Row-based: Poor cache locality for column scans, cannot compress columns independently
- Graph-based: Pointer chasing, poor SIMD utilization, complex memory management

## Decision
Use columnar storage where each attribute (subject, predicate, object, confidence, etc.) is stored in its own contiguous, SIMD-aligned column.

## Consequences

### Positive
- Sequential memory access enables prefetching and SIMD acceleration
- Each column can be compressed independently with optimal codec
- Dictionary encoding reduces storage for repeated values
- Bitmap indexes enable fast filtering

### Negative
- Updates require modifying multiple columns (handled by transactions)
- Joins between columns require coordination (handled by query engine)

## Alternatives Considered

| Alternative | Pros | Cons | Decision |
|------------|------|------|----------|
| Row-based (RDBMS) | Simple updates | Poor scan performance | Rejected |
| Graph (pointer-based) | Natural for relationships | Poor SIMD, cache misses | Rejected |
| Document (JSON) | Flexible schema | No column compression | Rejected |
| **Columnar (chosen)** | SIMD-ready, compressible | Complex updates | **Accepted** |
